# 직접 URL 스캔 이력 완료 정책

비교 기준은 `main`의 `119b02b`이다. 이 변경은 이력 저장 실패 처리를
보완하며 연구 당시 규칙·데이터·결과를 바꾸지 않는다. URL 규칙 **1.2**,
30/70 판정, 부모·포함 URL 점수의 `max` 결합과 요청별 HTTPS 가정 정보는
유지한다. 목록 조회·통계·Flutter·의존성은 변경하지 않는다.

## 횟수와 완료 상태

- `scan_count`, `first_seen_at`, `last_scanned_at`은 직접 URL 요청을 기록한다.
  이력 DB 저장의 성공 여부와 관계없이 기존처럼 횟수를 갱신한다.
- 최초 직접 URL 캐시 저장은 `direct_history_initialized=false`로 시작한다.
  횟수 갱신은 이 필드를 변경하지 않는다.
- 실제 `save_scan_result`가 `saved=true`를 반환한 뒤에만 캐시의 완료
  상태를 true로 갱신한다. 완료 갱신에 쓰는 캐시 주소는 분석 단계에서
  내부 필드로 전달하며 이력 DB와 API 응답에는 내보내지 않는다.
- 이력 저장 실패·예산 부족이면 완료 상태를 유지한다. 다음 직접 요청은
  현재 규칙의 캐시 점수를 재사용하면서 최초 이력 저장을 다시 시도한다.
- 이력 저장 성공 후 완료 표시까지 성공하면, 이후 같은 점수·판정은
  `history_saved=false`, `history_skip_reason=duplicate_unchanged`로 생략한다.
  위험 점수·판정 변경은 `risk_changed`, 규칙 변경에 따른 위험도 변경은
  `ruleset_reclassified` 이력을 저장하는 기존 정책을 유지한다. 규칙 버전만
  바뀌고 위험도가 같으면 기존처럼 중복 이력을 생략한다.
- 포함 URL은 직접 요청 횟수·자식 이력을 기록하거나 완료 표시를 하지
  않는다. QR 부모 이력만 저장한다. 포함 URL로 처음 생성된 캐시도 false로
  시작하며 최초 직접 요청의 이력이 성공해야 완료된다.
- 캐시 비활성화 시 완료 갱신 호출을 하지 않으며 기존 DB 저장 정책을 따른다.

## 예산과 실패 격리

완료 갱신은 실제 직접 URL 이력 저장 성공 후 최대 한 번의 조건부
`update_item`만 사용한다. 추가 조회나 재시도는 없다. 기존 캐시 SDK 설정
(호출 배분 최대 0.4초, 요청 마감 전 2초 여유, 총 시도 1회)을 그대로
사용하고 남은 예산이 부족하면 SDK 호출을 시작하지 않는다. 기존 12초
공유 예산과 socket timeout의 한계는 `ANALYSIS_TIME_POLICY.md`와 같다.
`attribute_exists(url_hash)` 조건으로 사라진 캐시를 완료 표시만 있는
항목으로 다시 만들지 않는다.

완료 갱신 실패·예산 부족은 이미 성공한 DB 이력을 실패로 바꾸지 않는다.
`db_saved=true`, `history_saved=true`와 저장 ID를 보존하며 내부 오류는
응답에 포함하지 않는다. 실패한 DB 저장은 기존 `db_saved=false`,
`history_saved=false`, `DATABASE_ERROR` 응답을 유지한다.

## 호환성과 동시 요청 한계

- 완료 필드가 없거나 true가 아니면 저장 완료를 확인할 수 없으므로 다음
  직접 요청에서 최초 이력 저장을 시도한다. 오래된 실제 성공 이력이 있으면
  한 번 더 저장될 수 있지만, 성공 후 완료 표시로 이후 중복을 생략한다.
- 기존 true 값은 호환성을 위해 완료 상태로 신뢰한다. 이전 코드가 DB 실패
  전에 잘못 true를 기록한 캐시는 이 변경만으로 복구할 수 없다. 실제 이력
  확인·정정은 별도 작업이며 이번에는 이력 조회나 마이그레이션을 추가하지 않는다.
- DB 저장과 캐시 완료 표시는 서로 다른 테이블의 별도 쓰기다. DB 성공 뒤
  갱신 실패·프로세스 종료·캐시 삭제가 발생하면 다음 요청에 중복 이력이 생길
  수 있다. DB 쓰기 응답 타임아웃도 실제 서버 저장 여부를 확정하지 못한다.
- 동시 요청들이 완료 표시 전에 pending 상태를 읽으면 각각 이력을 저장할
  수 있다. 횟수는 atomic ADD지만 이력은 요청별 UUID이며, 트랜잭션·분산
  잠금·멱등 키로 정확히 한 번 저장을 보장하지 않는다. 조건부 완료 갱신은
  캐시 존재만 확인하며 동시 분석 결과 갱신을 직렬화하지 않는다.
- 완료 필드는 최초 직접 이력의 존재만 나타낸다. 이후 위험도 변경 이력의
  DB 저장 실패에 대한 개별 재시도나 동시 변경 순서 보장은 기존 정책의
  한계로 남는다.

`test_direct_url_history.py`는 실제 캐시 분석·쓰기·횟수 갱신과
`persist_scan_history`·`save_scan_result`를 연결한다. VT와 DynamoDB SDK만
mock하고, 실패→성공→중복 생략, 포함 URL 캐시, 누락된 완료 필드,
완료 갱신 실패·예산 부족, 위험도·규칙 변경과 겹친 요청을 오프라인 검증한다.
