# 공학제 QR 분석 시간 정책

비교 기준은 `afaf924c066407684a3ca3e7244e9d3cc86df4fc`이다. 이 정책은 연구
평가 버전을 지칭하거나 연구 코드·데이터·기대값·평판 스냅샷·결과를 변경하지
않는다. URL 점수 규칙 **1.2**, 비URL 점수 규칙 2.0, 포함 URL 연결 정책 2.0,
30/70 판정과 `max(parent_score, embedded_url_max_score)` 결합은 유지한다.

## 확인한 기존 코드와 설정

- Flutter의 HTTP 응답 대기 제한은 15초다. 스캔 중 카메라를 멈추며, 시간
  초과·실패 시 일반 안내와 다시 스캔하기 버튼을 제공한다. 이번에 앱 코드를
  바꾸거나 타임아웃을 늘리지 않는다. 이전에 보완한 결과 화면은 평판 없음과
  링크 분석 미완료를 이미 구분한다.
- 명시적 링크 우선, 이후 검증된 후보를 중복 제거해 최대 3개 URL을 순차
  분석한다. 병렬 호출은 추가하지 않는다.
- 기존 VT 요청은 호출당 기본 10초였다. 코드에 명시적인 재시도·대기·폴링은
  없었다. 404일 때 기존 제출 활성화 설정에 따라 POST할 수 있었다.
  POST 접수 성공을 `available=true`로 반환하는 오류는 이번에 수정한다.
- 기존 DynamoDB resource에는 Config가 없어 SDK 기본 연결/읽기 제한
  60초와 환경·서비스별 재시도 정책에 영향을 받았다. 이는 SDK 소스의
  기본값이며 실제 운영의 적용값을 조회한 결과가 아니다.
- 로컬 `.env`에는 VT 활성화·404 제출이 true, VT 제한 10초, DynamoDB
  저장 비활성화가 기록되어 있다. 이 파일은 수정하지 않았다. 예제 설정의
  VT·제출·DB·URL 캐시는 false다. 프로세스 환경변수가 로컬 파일을 덮어쓸
  수 있으므로 이를 Lambda 운영 설정이라고 단정하지 않는다. 운영 Lambda
  제한, API Gateway/프록시 제한, 실제 캐시 활성화·재시도·AWS 자격증명
  공급 경로는 오프라인 작업에서 확인하지 않았다. 검증은 별도로 모든 외부
  호출을 차단하고 필요한 기능을 mock으로만 활성화한다.

## 선택한 예산

`/scan`, `/analyze-qr`의 분석 함수 진입 시 `time.monotonic()`으로 12초
마감 시각을 한 번 만든다. QR 파싱·URL 분석·캐시·이력 저장이 같은
ContextVar 예산을 사용한다. URL마다 마감 시각을 다시 만들지 않으며 요청
종료 시 컨텍스트를 복원한다. 벽시계는 캐시 시각·이력 시각에만 사용한다.

| 단계 | 호출별 최대 배분 | 요청 마감 전 남기는 시간 |
| --- | --- | --- |
| VT GET / 조건부 POST | 기존 VT 설정과 3초 중 작은 값 | 2초 |
| 캐시 조회·카운터·저장·메타데이터 갱신 | 0.4초 | 2초 |
| 이력 DB 저장 | 0.75초 | 1초 |

각 배분은 현재 남은 시간에 맞춰 더 줄어든다. 연결에 25%, 읽기에 75%를
배분하며, 배분 가능 시간이 0.05초 미만이면 호출을 시작하지 않는다.
2초 여유는 저장과 결과 정리용이며 그중 마지막 1초는 응답 정리·직렬화용이다.
마지막 1초에 들어가면 새 로컬 URL 분석도 시작하지 않는다. 완료한 결과는
시간이 지났다는 이유로 버리지 않는다. 예산 소진으로 작업을 시작하지 못하면
`analysis_flags.analysis_budget_exhausted=true`를 제공한다.

12초 목표와 앱 15초 사이의 3초는 통신·스케줄링 등의 여유다. 이는 정상적인
짧은 실패 응답을 목표로 잡은 배분이며 운영 지연을 측정해 보장한 수치가 아니다.
코드에 새 환경변수나 의존성을 추가하지 않는다. 제출 조건을 자동으로 켜지
않으며 기존 enabled + API key + 404 + 제출 설정 조건을 유지한다.
VT는 한 번만 시도하고 리디렉션을 따라가지 않는다. 429의 Retry-After를
기다리거나 자동 재시도하지 않으며 제출 후 폴링하지 않는다.
DB/캐시는 standard 재시도 모드의 `total_max_attempts=1`로 재시도를 막는다.
남은 예산이 부족하면 resource 생성 자체를 시작하지 않는다.

## 실패와 캐시의 의미

- URL 로컬 분석을 먼저 완료하고 VT 정보를 결합한다. 타임아웃·429·조회
  오류·잘못된 리포트·리포트 없음은 로컬 점수·판정을 바꾸지 않고
  `vt_available=false`와 일반 사유로 반환한다. 내부 예외, 설정 안내,
  원본 외부 오류 응답을 사용자 응답에 넣지 않는다.
  이때 호환용 VT 숫자 필드의 0은 확인된 악성 탐지 0건을 의미하지 않는다.
- 새 `vt_lookup_status`는 `available`, `disabled`, `timeout`, `rate_limited`,
  `lookup_failed`, `report_missing`, `submitted`, `budget_exhausted`, `cached`를
  구분한다. 직접 URL과 포함 URL의 실제 API 직렬화에 보존한다.
  필드 없는 이전 응답은 조회 성공이라고 보완하지 않는다.
- 제출 접수는 `submitted`이고 완료된 평판이 아니다. 탐지 수가 없는
  리포트도 악성 탐지 0건으로 해석하지 않는다. 과거 `submitted_analysis`
  캐시는 신선한 평판으로 재사용하지 않고 다시 계산한다.
- 예산이 외부 호출만 막은 경우, 로컬 URL 결과는 성공 목록에 남고
  외부 평판만 미확인이다. 로컬 분석 시작 여유도 없거나 로컬 분석 자체가
  실패하면 기존 고정 실패 코드와 `embedded_url_analysis_complete=false`를
  사용한다. 성공한 다른 링크와 부모 점수는 보존한다. 3개 제한으로 제외된
  링크는 기존 skipped count로 별도 표시한다.
- 현재 규칙의 신선한 캐시는 재사용하고 `vt_lookup_status=cached`로 평판
  재조회 성공과 구분한다. 신선한 로컬 전용 캐시는 평판 없음 상태를 유지한다.
  이전 버전·누락 버전은 1.2 계산을 거쳐야 하며 실패 시 이름만 바꾸지 않는다.
- 실패한 VT 조회는 `vt_checked_at`을 갱신하지 않는다. 새 로컬 전용 캐시의
  `last_checked_at`은 로컬 계산 시각이며 VT 성공 시각이 아니다.
  `cache_revalidated`만으로 VT 성공을 판단하지 않는다. 로컬 전용 결과는
  기존 캐시 TTL 동안 재사용될 수 있으므로 평판 복구를 즉시 재조회하지 않는
  한계가 있다.
- 오래된 평판 위험 근거는 기존 정책대로 점수에 보존하되, 이번 재조회
  실패 응답은 `vt_available=false`, `vt_source=cached_report`, 실패 상태와
  `historical_reputation_used` 플래그를 제공한다. 과거 통계를 악성 탐지 0건으로
  바꾸지 않으며 과거 평판 사용 사유도 남긴다. 버전 변경 시에는 로컬 점수를
  새 규칙으로 다시 계산해 결합한다. 과거 조회 시각을 최신으로 바꾸지 않는다.
- 캐시 쓰기 실패·예산 부족은 이미 계산한 결과를 버리지 않는다. DB 저장
  실패·예산 부족도 기존 `db_saved=false`, `DATABASE_ERROR` 정책을 유지한다.
  `assumed_https`와 원본 후보는 계속 요청별 응답에서만 구성한다.

## 절대 실행 시간 상한이 아닌 이유

이것은 협력적으로 새 작업을 중단하는 시간 예산이며 12초 강제 취소가 아니다.
실제 확인한 Requests adapter는 연결/읽기 timeout을 urllib3에 전달한다.
urllib3 Timeout 소스는 DNS가 socket timeout을 따르지 않으며 읽기 timeout이
수신 사이의 대기 시간을 측정한다고 설명한다. 여러 IP 연결 시도, 느린 연속
수신, 운영체제 스케줄링, 응답 파싱은 배분보다 오래 걸릴 수 있다.
botocore도 같은 socket 계열 연결/읽기 timeout을 사용한다. boto3 resource
생성·자격증명 조회/갱신·DNS는 해당 서비스 Config로 모두 제한되지 않는다.
SDK가 시작된 호출은 이 예산이 즉시 중단시키지 못한다.

예산이 감지할 수 있는 시점은 블로킹 호출이 반환된 이후다. 긴 호출이
예산을 넘겨 돌아오면 완료한 로컬 결과를 보존하고 이후 호출·URL 분석·저장을
중단한다. 결과 정리·직렬화 여유 역시 예약한 여유이지 직렬화 자체의 강제
timeout이 아니다. HTTP 수신·검증, 스레드 큐 대기, Lambda cold start와
네트워크 전달도 분석 함수 예산 밖이다. 따라서 앱이 항상 15초 안에 받는다는
보장은 없다. Flutter의 Future.timeout도 원래 요청과 서버 처리를 취소하지
않는다. 절대 상한이 필요하면 운영 제한 확인과 실행 격리/취소 설계가 별도로
필요하며, 이번에는 백그라운드 스레드나 병렬 VT 호출을 추가하지 않는다.

검증은 `test_analysis_budget.py`의 가짜 monotonic 시계, mock VT/SDK와 실제
API 응답 모델로 수행한다. 실제 sleep, 위험 URL 접속, VT 제출·운영 호출은
하지 않는다. 기존 공개 백엔드 회귀 테스트도 함께 실행한다. 연구 디렉터리는
테스트 수집 대상이 아니며 Python 3.12 운영 실행은 별도 확인 항목이다.
